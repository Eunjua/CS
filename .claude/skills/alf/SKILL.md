# ALF 개선 스킬 — 상담 분석 → 규칙 개선 → 로그 누적 사이클

케어아카데미 AI 상담봇(ALF)의 응대를 **실제 상담 내역으로 점검하고, 규칙을 고치고, 개선 이력을 누적**하는 반복 사이클. 은주가 `cs-triage/상담내역/`에 파일을 올리고 부르면 아래 절차를 끝까지 돈다.

## 꼭 지킬 것

- **🧩 ALF는 「태스크」와 「규칙」 두 층으로 움직인다 — 무엇을 어느 층에서 고칠지부터 가른다.**

| | 태스크 | 규칙 (`ALF_rules/`) |
|---|---|---|
| 언제 | **트리거 조건에 맞으면 대화 시작 시점에 실행** | 태스크가 도는 중에도 **모든 응답에 항상 적용** |
| 무엇을 | **노드 흐름으로 대화를 직접 제어** — 번호 수집, API 조회, 분기 안내 같은 **구체적 동작** | 톤앤매너, 금지 표현, 상담원 연결 조건 등 **응답의 방향과 태도** |
| 단독 동작 | — | **태스크가 없는 일반 문의는 규칙만으로 답변** |

  > ✅ **판정 전 자문**: 지금 보는 현상이 *흐름*인가(태스크) *말투·판단 기준*인가(규칙)? **흐름이면 규칙 개정을 제안하지 않는다** — 규칙만 고쳐 동작을 바꾸려다 11차에 두 번 실패했다.

- **숫자는 `measure.py` 출력에서만.** 손으로 세지 않는다. 분모·완결률·이탈률 정의는 [reference/metrics.md](reference/metrics.md).
- **완결률과 이탈률은 항상 한 줄에 붙여 보고한다.** 이탈이 늘면 완결률이 같이 올라가므로, 떼어 쓰면 악화를 개선으로 읽는다.
- **`alfTriggered=false`는 분모에서 뺀다.** ALF가 발동조차 안 한 건은 봇의 성과로도 실패로도 셀 수 없다.
- **두 잣대를 구분한다.** 말투·태도·이관 판단 = `ALF_rules/` 7종 + 구분기준 통합본 / 사실관계 = `ALF_docs/` + `ALF_FAQ/`. **"docs에도 FAQ에도 없어야 공백"이다.**
- **⚠️ 해소 판정은 2회 연속 재발 없음일 때만.** 한 회차 0건은 "재발 없음"이지 해소가 아니고, **사례 0건은 해소가 아니라 검증 불가**다.
- **🔴 미해결 항목은 매 회차 전건을 훑는다.** 신규만 보고하면 지난 회차 항목이 조용히 사라진다(실제로 5건이 끊겼다).
- **새 파일만 분석한다.** `상담내역/` 바로 아래만 본다. `처리완료/` 안은 건드리지 않는다.
- **개선은 제안하고 승인받는다.** 규칙 파일 수정은 "이렇게 고칠게요" 먼저 보여주고 승인 후 반영.
- **이력은 무조건 남긴다.** ① 개선로그 ② 노션 DB 둘 ③ 기준표 엑셀. "지난번 고친 게 이번엔 좋아졌나"를 추적하는 게 이 스킬의 핵심 가치다.

## 스크립트

```bash
S=.claude/skills/alf
python3 $S/measure.py cs-triage/상담내역/*.xlsx --out <저장소 밖 폴더>   # 지표 + 건별 판정표 CSV
python3 cs-triage/archive_log.py --apply                              # 로그 아카이브(7번 뒤 항상)
```

스크립트를 고치면 `measure.py --selftest`를 돌린다. 건별 CSV에는 상담 링크가 들어가므로 저장소 밖에만 쓴다.

## 진행 순서

1. **새 상담 파일 수집.** `cs-triage/상담내역/` 바로 아래(하위 `처리완료/` 제외)를 찾는다. 없으면 "상담내역 폴더에 새 파일이 없어요. 분석할 상담을 `cs-triage/상담내역/`에 올려주세요"라고 안내하고 멈춘다. 있으면 몇 건/어떤 파일인지 먼저 알린다.

2. **잣대 로드.** 구분기준 통합본 2장(판단기준)과 ALF_rules 7종, `ALF_개선로그/최신_*.md`의 **"다음 점검 때 확인할 것"**을 읽는다. 직전에 고친 규칙을 우선 확인 대상으로 삼는다. **태스크 export도 최신 파일을 열어 노드 목록을 뽑고, 직전 파일과 달라진 노드가 있는지 본다.** → [sources.md](reference/sources.md)

2-1. **🔴 미해결 전건 목록을 먼저 뽑는다.** 📊 추적 DB에서 `완료/해소`가 아닌 행을 **전부** 가져온다.
   ```sql
   SELECT "회차", "개선점", "상태", "확인 방법", "다음 분석 결과"
   FROM "collection://e6e40c92-555c-4c6f-ac31-1f24a7517fa6"
   WHERE "상태" != '완료/해소'  ORDER BY "date:점검일:start"
   ```
   - 나온 행 전부 + 이번 배치 신규 발견 = **이번 회차 확인 목록**. 각 행의 `확인 방법` 칸이 무엇을 세면 되는지다.
   - **`미확인` 행은 특히 눈여겨본다**(추적이 끊긴 것들). 그중 상담 분석이 필요 없는 것(설정 확인·목록 대조·정책 결정)은 이번 세션에서 바로 결론 내자고 제안한다.
   - 10건이 넘으면 우선순위: 고객 피해 직결(기한·비용 오안내) → 건수 큰 것 → 3회 이상 이월.

3. **`measure.py` 실행 후 상담 한 건씩 판정.** 스크립트가 분모·완결률·이탈률·검증식·봇 발화 유무를 내주고, 건별 CSV가 판정의 바탕이 된다. 판정은 **① 유형 분류 → ② 이관 적정성 등급 → ③ 사실관계** 순. → [judge.md](reference/judge.md) · [metrics.md](reference/metrics.md)

4. **기준표 엑셀 누적.** `분석` 시트에 건별로 이어 붙이고, 6개 집계시트·요약 시트에 일자별 건수를 더한다. **H열은 절대 건드리지 않는다.** → [excel.md](reference/excel.md)

5. **분석 결과 표로 정리.** 사용자에게 보여준다.
   ```
   | # | 유형 | 처리(완결/이관/이탈) | 판정 | 근거(태그·발화) | 개선 액션 |
   ```
   - 끝에 **종합**: 1) 분모 산출 과정 2) **완결률과 이탈률을 한 줄에 붙여서** 3) 등급 분포(✅·⚠️·❌·🚫제외) 4) `AI상담/*` 태그 건수 5) 가장 반복된 문제 1~2개 6) 직전 점검 대비 변화.
   - 🔴 **집계 정의가 바뀐 회차라면 종합 맨 앞에 무엇이 어떻게 바뀌었는지 먼저 쓴다.** [metrics.md](reference/metrics.md)에 미보고 개정이 있으면 그 문단을 그대로 옮긴다.

5-1. **🔴 미해결 전건 결과표.** 2-1의 확인 목록을 **한 줄도 빠뜨리지 않고** 낸다.
   ```
   | 회차 | 개선점 | 직전 상태 | 이번 결과 | 새 상태 |
   ```
   - **사례가 0건이어도 반드시 한 줄 쓴다** — `사례 0건 — N회째 이월`. 빈칸·생략 금지.
   - 판정 문구는 넷 중 하나로 시작: `✅ 확인` / `🟡 부분` / `❌ 그대로·악화` / `🔲 검증 불가(사례 0건)`.
   - **3회 연속 `🔲 검증 불가`면 은주에게 묻는다** — "봇에 직접 테스트 문의를 넣어 우회 검증할까요, 그냥 닫을까요, 계속 대기할까요?"
   - **`미확인`(추적 끊김) 행은 회차당 최소 1건은 결론 낸다.**
   - `완료/해소`를 주려면 **2회 연속 재발 없음**인지 먼저 확인한다. 1회차째면 `계속 추적`으로 두고 "1회차 재발 없음 — 다음 회차에 한 번 더 보고 닫는다"라고 적는다.

5-2. **📐 docs 역방향 점검 (상시).** 봇 발화 중 **docs에 없거나 docs와 반대인데 실제로는 맞는 안내**가 있으면 docs가 낡은 것이다. 은주에게 **"지난 회차 이후 제품에 붙은 기능이나 바뀐 정책이 있나요?"**를 묻는다 — 이 질문이 가장 확실하다.

5-3. **🔀 FAQ ↔ docs 충돌 점검 (상시).** FAQ 15개 안팎의 주제를 docs와 대조해 ⓐ 한쪽에만 있는 것 ⓑ 양쪽에 있는데 내용이 다른 것을 뽑는다. 금액·정책처럼 **한쪽에만 있는 숫자**가 특히 위험하다.

6. **개선 제안.** 문제 유형에 맞는 곳을 짚는다.
   - **흐름 문제(태스크 층)** → 규칙 개정을 제안하지 않는다. `ALF_task/` 최신 파일에서 원인 노드를 찾아 **노드 단위로** 제안한다: 1) 노드 이름·유형 2) 원인이 된 현재 문구·분기 조건 인용 3) 채널톡 AI에 그대로 붙여 넣을 수정 요청문(코드 블록) 4) 테스트할 고객 문장.
   - **말투·태도·이관 문제** → 어느 `ALF_rules/*.md`(또는 구분기준 통합본)를 어떻게 고칠지. **2000자 제한**을 확인한다.
   - **사실관계 오답·지식 공백** → **docs와 FAQ 중 어디에 넣을지 먼저 정한다.** 짧고 답이 하나로 떨어지면 FAQ, 조건에 따라 갈리면 docs, 둘 다 필요하면 **내용을 같게** 맞춘다. docs는 파일 수정 후 **채널톡 등록까지 확인**하고, FAQ는 파일을 만들지 말고 「무엇을/어떻게/왜(chatId)」 세 줄로 글로 전달한다.
   - **승인받은 것만** 실제 파일에 반영한다.

7. **로그 누적.** `ALF_개선로그/최신_*.md`에 이번 회차를 추가하고 현황 요약을 갱신한 뒤, `archive_log.py --apply`를 돌린다. → [log-format.md](reference/log-format.md)

8. **노션 갱신 — DB 둘이 먼저, 페이지가 나중.** 📊 추적 DB(5-1 전건 상태·신규 행) → 📈 추이 DB(이번 회차 행 **필수**) → 추적 페이지(4블록 유지, 직전 회차는 아카이브로). → [notion.md](reference/notion.md)

9. **처리완료 이동.** 분석 끝난 상담 파일을 `cs-triage/상담내역/처리완료/`로 옮긴다(원본 보존). `git mv`가 안 되면(미추적 파일) 일반 `mv`.

10. **CX 실행 과제 보드 연결.** 이번 회차 개선점 중 **이 세션에서 못 끝내고 따로 시간을 잡아야 하는 것**이 있는지 본다.
    - **올리지 않는 것**: 규칙 파일 수정·docs 보강·문구 교체(추적표가 이미 관리 — 보드에 넣으면 이중 관리).
    - **올릴 것**: 백엔드 조회·실행 연동 확대처럼 몇 시간~며칠을 잡아야 하는 작업.
    - 있으면 **반드시 물어본다** — *"이건 따로 시간이 필요해 보이는데, CX 보드에 올릴까요?"* 자동으로 넣지 않는다.
    - 넣을 때: DB `collection://5a294352-cc03-4c24-a828-be09a28dbc91` / `연결`=KR2 AI상담 · `분기`=26-3Q · `유형`=실행 · `우선순위`는 물어보고 · **`착수일`은 비워둔다** · `메모`에 근거(회차·수치).
    - **반대 방향도 본다**: 보드에 이미 있는 ALF 과제(예: 「ALF 백엔드 조회·실행 연동 확대」)가 진전됐으면 `상태`·`메모` 갱신을 제안한다. 보드 운영 규칙 전체는 `/과제기록`(`~/.claude/commands/과제기록.md`) 참고.

11. **마무리.** 변경 요약(분석 N건 / 규칙 수정 M건 / **미해결 전건 N건 판정** / 로그·노션 DB·엑셀 갱신 / 파일 이동 / 보드 반영)을 보고하고 "GitHub에 push할까요? (`cspush`)"를 묻는다.
    - **보고 전 자가 점검 4가지**: 1) 2-1 확인 목록 행 수 = 5-1 결과표 행 수인가 2) `완료/해소`로 바꾼 행이 전부 2회 연속 재발 없음인가 3) `미확인` 행 중 이번에 결론 낸 것이 최소 1건인가 4) 📈 추이 DB 행 수가 회차 수와 같은가. **안 되는 게 있으면 그 사실을 그대로 보고한다** — 조용히 넘기면 그게 추적이 끊기는 순간이다.

## 주의

- 비개발자다. 유형 코드·규칙 위반을 짚을 땐 "왜 그게 문제인지" 한 줄로 쉽게 설명한다.
- 상담 내역에 고객 개인정보(이름·전번·주소)가 있으면 로그·노션에 그대로 옮기지 말고 마스킹하거나 "○○ 고객"으로 익명화한다.
- 규칙 파일 수정·로그 저장은 사용자 확인 후. 파일 삭제는 하지 않는다(이동만).
- 상담 건수가 많으면(수십 건+) 유형별로 묶어 표본·패턴 위주로 정리하고, 무엇을 표본으로 골랐는지 밝힌다.
