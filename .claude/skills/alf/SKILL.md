# ALF 개선 스킬 — 상담 분석 → 규칙 개선 → 로그 누적 사이클

케어아카데미 AI 상담봇(ALF)의 응대를 **실제 상담 내역으로 점검하고, 규칙을 고치고, 개선 이력을 누적**하는 반복 사이클. 사용자(은주, CX Manager)가 `cs-triage/상담내역/`에 파일을 올리고 부르면 아래 절차를 끝까지 돈다.

## 핵심 원칙
- **새 파일만 분석한다.** `상담내역/` 바로 아래의 파일만 본다. `처리완료/` 안은 이미 분석한 것이므로 건드리지 않는다.
- **상담 파일은 엑셀(.xlsx)이다.** 파이썬(`mcp__plugin_oh-my-claudecode_t__python_repl` 또는 Bash의 `python3` + `openpyxl`/`pandas`)으로 읽어 대화 내용을 추출한다. 컬럼 구조가 처음 보는 형태면 먼저 상단 몇 행을 출력해 구조를 파악한 뒤 분석한다.
- **두 잣대를 구분한다.** **말투·태도·이관 판단 = `ALF_rules/` 7종 + 구분기준 통합본**, **사실관계·정답 여부 = `ALF_docs/` 봇 지식 도큐먼트**. 봇 답이 "불친절"인지 "사실이 틀림"인지를 이 둘로 갈라 판정한다.
- **개선은 제안하고 승인받는다.** 규칙 파일(`ALF_rules/*.md`) 수정은 사용자 비개발자임을 감안해 "이렇게 고칠게요" 먼저 보여주고 승인 후 반영.
- **이력은 무조건 남긴다.** 한 번 돌 때마다 ① `ALF_개선로그.md`(정본)에 날짜·문제·액션·다음 확인사항을 누적하고, ② **노션 추적 DB**(개선점·확인방법·상태·다음결과)에 반영하고, ③ **기준표 통합본 엑셀 `분석` 시트**에 건별 분류를 이어 붙인다. "지난번 고친 게 이번엔 좋아졌나"를 추적하는 게 이 스킬의 핵심 가치다.
- **🔴 미해결 항목은 매 회차 전건을 훑는다.** 이번 배치에서 새로 발견한 것만 보고하면 지난 회차의 `부분 확인`·`계속 추적`·`미확인`이 조용히 사라진다. 2~10차를 전수 점검했더니 **결과 칸이 빈 채 추적이 끊긴 항목이 5건** 있었다(봇 제공목록 동기화 · 취업 과장 방지 규칙 · docs 미반영 6종 · 교재 링크 후속 · 운영시간외 멘트 설정). 회차마다 "다음 점검 때 확인할 것"을 5~7개로 새로 쓰다 보니 급한 신규 이슈가 오래된 항목을 밀어낸 것이다. → **진행순서 2-1에서 미해결 전건을 먼저 뽑고, 8번에서 그 전건에 결과를 적는다. 빈칸으로 두지 않는다.**
- **⚠️ 해소 판정은 2회 연속 재발 없음일 때만 한다.** 8차에 "docs 연동 해결"로 닫았다가 9·10차에 재발해 판정을 철회한 전례가 있다. **한 회차 0건은 "재발 없음"이지 "해소"가 아니다.** 그리고 **사례가 0건이면 해소가 아니라 검증 불가**다 — 이 둘을 절대 섞지 말 것(폭언 규칙은 사례가 없어 4회째 판정 불가지, 해결된 게 아니다).
- **📐 docs는 양방향으로 본다.** 지금까진 "봇이 docs를 따르나"만 봤는데, 10차에 **반대 방향이 2건** 나왔다(배송현황 조회·기출문제) — **제품에 기능이 생겼는데 docs가 낡아서, docs가 봇에게 틀린 지시를 하고 있었다.** 봇이 맞게 답하거나(배송) 문의 사례가 없으면(기출) 분석으로는 영원히 안 잡힌다. 둘 다 은주가 docs를 직접 읽다 발견했다. → 회차마다 **"docs가 현재 제품과 맞나"를 따로 묻고, 최근 제품 변경이 있었는지 은주에게 확인한다.**
- **🎭 지표 하나만 보면 반대로 읽힌다.** 10차에 "봇 첫 발화 번호선요구 23.5%→2.5%"를 개선으로 볼 뻔했는데, 앞에 접수 멘트가 끼면서 번호 요구가 둘째 발화로 밀린 **지표 착시**였다. 실질 지표(답변보다 먼저 번호만 요구)는 65%→63%로 제자리. **개선으로 보이면 다른 각도의 지표로 한 번 더 재고, 정의를 결과에 명시한다.**
- **봇 발화는 5차(2026-07-10)부터 export에 포함된다.** `Message data` 시트의 `personType='bot'`. 말투·정확도 직접 채점이 가능하다. 단 **새 export를 받으면 먼저 bot 발화가 있는지 확인**하고, 없으면 이관 적정성 축으로만 판정하고 그 한계를 결과에 명시한다.
- **AI 관여 판정은 `alfTriggered` 필드로 한다.** UserChat 시트의 `alfTriggered=false`인 건은 ALF가 발동조차 안 한 것이라 봇의 성과로도 실패로도 셀 수 없다 → **분모에서 뺀다.** (2026-08-06 은주 확정)
  - ⚠️ **태그(`AI/상담완료`·`AI/상담원이관`)로 판정하면 안 된다.** 9차에 시험해 보니 **ALF가 실제로 응대했는데(봇 발화 최대 19건) 태그만 안 붙은 건이 11건** 있었다. 태그는 사람이 붙이는 것이라 누락된다. `alfTriggered`는 시스템이 찍으므로 신뢰할 수 있다.
  - 상담원 발화가 있다는 이유로 "이관"으로 세지 말 것. 그러면 봇이 등장할 기회조차 없던 건까지 ②(자동화 여력)에 들어간다.
- **`AI상담/*` 태그가 봇 발화를 대신하는 직접 품질신호다.** 사람(상담원·은주)이 "AI 응대에 문제 있음"이라고 손으로 붙인 태그다. `AI/*`(상담완료·상담원이관)는 워크플로우 **정상 상태**라 등급에 안 쓰고, **`AI상담/*`만 문제 신호**로 쓴다. 아래 진행순서 3번의 등급·태그 매핑 참고.
- **규칙은 2000자 제한.** `ALF_rules/*.md` 한 파일은 채널톡 한 규칙으로 들어가며 **2000자(문자·숫자·특수문자·공백 전부 포함)**를 넘으면 안 된다. 수정·압축 시 `python3 -c "print(len(open(...).read()))"`로 글자수를 확인한다. **멘트는 규칙에 넣지 말고 "언제 상담을 열지" 조건만** 쓴다(멘트+상담열기를 함께 넣으면 상담 열기가 실패). 연결 멘트는 자동 전송되나 **사과는 미포함**(사과는 담당자가 응대 시 전함).

## 진행 순서

1. **새 상담 파일 수집.** `cs-triage/상담내역/` 바로 아래(하위 `처리완료/` 제외)의 파일을 모두 찾는다.
   - 파일이 없으면: "상담내역 폴더에 새 파일이 없어요. 분석할 상담을 `cs-triage/상담내역/`에 올려주세요"라고 안내하고 멈춘다.
   - 있으면 몇 건/어떤 파일인지 먼저 알린다.

2. **잣대 로드.** 위 "잣대가 되는 파일" 중 구분기준 통합본 2장(판단기준)과 ALF_rules 7종, 그리고 ALF_개선로그.md의 **"다음 점검 때 확인할 것"** 항목을 읽는다. 직전에 고친 규칙이 이번 상담에서 실제로 개선됐는지 우선 확인 대상으로 삼는다.

2-1. **🔴 미해결 전건 목록을 먼저 뽑는다 (이번 회차 확인 목록).** 직전 회차 것만 보면 오래된 항목이 밀려나므로, **DB에서 `완료/해소`가 아닌 행을 전부** 가져온다.
   ```sql
   SELECT "회차", "개선점", "상태", "확인 방법", "다음 분석 결과"
   FROM "collection://e6e40c92-555c-4c6f-ac31-1f24a7517fa6"
   WHERE "상태" != '완료/해소'
   ORDER BY "date:점검일:start"
   ```
   - 나온 행 전부가 **이번 회차 확인 목록**이다. 여기에 이번 배치의 신규 발견을 더한다.
   - 각 행의 `확인 방법` 칸이 곧 무엇을 세면 되는지다. 그대로 측정한다.
   - **`미확인` 행은 특히 눈여겨본다** — 추적이 끊긴 것들이라 아무도 안 보고 있다. 그중 **상담 분석이 필요 없는 것**(설정 화면 확인·목록 대조·정책 결정)은 이번 세션에서 바로 결론 내자고 은주에게 제안한다.
   - 확인 목록이 10건을 넘으면 우선순위를 매긴다: ① 고객 피해가 직결되는 것(기한·비용 오안내) → ② 건수가 큰 것 → ③ 3회 이상 이월된 것.

3. **상담 한 건씩 판정.** 각 상담에 대해 **① 유형 분류 → ② 이관 적정성 등급 → ③ 사실관계** 순으로 매긴다.

   **① 유형 분류 결정 트리** (위→아래, 처음 걸리는 곳에서 확정. 봇 발화 없이 user 발화+태그로 판정)
   ```
   -1. [AI 관여 게이트 — 무조건 맨 먼저]
      alfTriggered = false? ─────────────────────────→ 🚫 제외(집계 대상 아님)
         ALF가 발동조차 안 한 건. 봇의 성과로도 실패로도 셀 수 없다.
         ※ 태그가 아니라 이 필드로 판정한다(태그는 누락된다).
   0. [2-0 레드라인]
      금전작업·개인정보변경·신원오등록? ──────────────→ ③실작업
      화남·불신·전화고집·디지털취약 발화? ───────────→ ③감정
         └ AI상담/상담원요청 태그(고객이 사람 직접요청)도 → ③감정
   1. 앱·영상·오답 등 기술장애 + 안내 후에도 재발? ────→ ③기술
   2. manager(사람) 발화 0개?          ※태그가 아니라 실제 발화로 판정
         ├ AI상담/* 문제태그 없음 ──────────────────→ ① 봇완결
         └ AI상담/고객이탈 있음 ───────────────────→ △ 이탈(미완결)  ※①로 세지 않음
   3. manager 발화 있음(=이관) → 답이 표준 안내로 가능?
         백엔드 조회·수정 필요(배송·입금·주소)? ─────→ ②-B
         말·파일만으로 끝? ──────────────────────→ ②-A
               docs에 있는데 이관 → ②-A-① / docs에 없어 이관 → ②-A-②
   ```
   > ⚠️ **-1번을 건너뛰면 안 된다.** "상담원 발화가 있으면 이관"으로 판정하면 **봇이 등장할 기회조차 없던 건까지 ②(자동화 여력)로 세어** 봇완결률이 실제보다 낮게, 없앨 수 있는 이관이 실제보다 많게 나온다. 9차(2026-08-06)에 161건 중 **12건이 ALF 미발동**이었고, 처음에 이를 안 걸러 봇완결률이 36%(실제 46.3%)로 과소 보고됐다.
   **타이브레이커(경계 애매할 때):** 복합문의=가장 무거운 갈래로(FAQ+환불→③) / 명시적 사람·전화요청=③감정 / 기술장애는 1회 안내로 풀리면 ②-A·재발하면 ③기술.

   **② 이관 적정성 등급** (봇 말투 채점 대신 "처리가 맞았나"로 판정)

   | 등급 | 뜻 | 판정 근거 |
   |---|---|---|
   | 🚫 제외 | ALF 미발동 | `alfTriggered = false` → 분모에서 뺀다 |
   | ✅ 적정 | 처리가 맞았음 | ① 봇완결 / ③ 정당한 이관(사람이 진짜 필요) |
   | ⚠️ 없앨 수 있는 이관 | 봇이 풀 수 있었는데 사람이 받음 | ②-A·②-B 인데 이관 |
   | ❌ 놓침 | 봇 응대 실패 | `AI상담/오안내`(오답) · `AI상담/이관안함`(미이관) |
   | △ 이탈(미완결) | 결과 미상, ✅로 세지 않음 | `AI상담/고객이탈`(전번요청·상담원제안에 무응답 이탈) |

   > **핵심 1:** `AI/상담완료`로 찍혔어도 `AI상담/*` 문제태그가 있으면 겉보기 완결이다 — ①(봇완결)에서 빼서 △ 또는 ❌로 분류한다.
   > **핵심 2:** `alfTriggered=false`인 건은 아예 분모에서 뺀다. 이 둘을 지켜야 봇완결률이 정직해진다.

   **📐 봇완결률(AI 해결율) 계산식**
   ```
   분모 = (alfTriggered = true) − (AI상담/고객이탈* 건)
   분자 = ① 봇완결 (= 분모 중 manager 발화 0 · 오안내/이관안함 태그 없음)
   ```
   회차 보고에는 **분모 산출 과정을 반드시 밝힌다** — 예: `전체 161 → alf발동 149 → 이탈 13 제외 → 분모 136 / 봇완결 63 = 46.3%`.

   **별도 관찰 신호** (등급 아님, 회차별 건수만 집계해 추적):
   - `AI상담/고객이탈` — 봇 이관 흐름(전번 요청)이 고객을 이탈시키는지. 반복되면 개선 포인트.
   - `AI상담/상담원요청` — ③감정으로 분류(사람 직접요청).
   - `AI상담/고객정보미입력` — 봇 정보수집 실패.

   **③ 사실관계 판정 (ALF_docs 기준)**: `AI상담/오안내` 태그가 붙은 건이나 내부메모상 오답 의심 건을 `ALF_docs/` 해당 도큐먼트와 대조한다.
     - 도큐먼트와 다르게 답함 → ❌오답 (어느 도큐먼트의 무엇과 어긋나는지 명시)
     - 도큐먼트에 항목이 아예 없어서 못 답함/이관 → ②-A-② **도큐먼트 공백** (어느 도큐먼트에 무엇을 추가해야 하는지)
     - `ALF_docs/`가 비어 있으면 사실관계는 "도큐먼트 미등록"으로 보류.

4. **엑셀 분석 시트 누적.** 판정한 배치를 건별로 `cs-triage/케어아카데미_AI사람_기준표_통합본.xlsx`의 **`분석` 시트**(구 `이관사유_상세`, 같은 시트)에 이어 붙인다.
   - 시트명은 유니코드 정규화(NFC/NFD) 차이가 있을 수 있으니 `unicodedata.normalize('NFC', s)`로 매칭해 찾는다. 시트명이 바뀌어 있으면 그 시트를 쓴다.
   - 컬럼: **A 순번**(기존 마지막 순번 이어서) · **B id** · **C url** · **D 태그(원본)** · **E 분류태그**(원본 `아카데미_` 태그에서 접두어 제거, 없으면 빈칸) · **F 5단계 분류**(①/②-A/②-B/③실작업/③감정/③기술, **ALF 미발동은 `제외`**) · **G 이관 사유**(한 줄) · **I 없앨수있는이관**(②=Y / ③=N / ①·제외=-).
   - **H 열(은주 확인/이관 이유)은 절대 건드리지 않는다**(은주 수기 확인용, 항상 공백으로 남김).
   - id·url·태그·`alfTriggered`는 UserChat 시트에서, manager 발화 유무는 Message data 시트에서 뽑는다. F·G·I는 step 3 판정 결과를 쓴다. (① → I="-", 이관건은 ②=Y·③=N)
   - **ALF 미발동 건도 행은 남긴다**(추적용). 단 F열에 `제외`, G열에 "ALF 미발동(alfTriggered=false)"이라 적고 **집계시트에는 넣지 않는다.**
   - openpyxl로 append 전 **원본을 한 번 백업**(스크래치패드 복사)하고 저장한다. 기존 행은 보존(append-only).

4-1. **유형별 집계시트에 일자별 건수 추가.** 같은 엑셀의 **6개 집계시트**(`집계_①현재AI` · `집계_②A즉시자동화` · `집계_②B시스템연동` · `집계_③실작업` · `집계_③감정전화` · `집계_③기술오류`)에 새 상담을 **상담 날짜(createdAt)별 열**로 이어 붙인다(열 헤더 예 `06-22`). 여러 export 파일을 함께 받으면 **id로 중복 제거(union)** 후 날짜 집계한다. 배치에 섞인 아주 오래된 소량 날짜는 `~MM-DD` 한 열로 묶어도 된다.
   - **건별 실제 판정으로 배정**: 봇완결(manager 발화 0)=`①현재AI` / 이관건은 세부태그의 대분류로. 그래서 **같은 세부태그(예 일자리)가 완결분은 ①시트, 이관분은 ②-A시트에 각각** 나뉘어 들어간다.
   - **🚫 ALF 미발동 건(`alfTriggered=false`)은 6개 시트 어디에도 넣지 않는다.** 상담원 발화가 있다고 이관으로 세면 안 된다 — 봇이 등장할 기회조차 없던 건이다.
   - **단, `AI상담/고객이탈` 태그 건은 manager 발화가 0이어도 ①현재AI에서 뺀다**(겉보기 완결=미완결). △이탈로 따로 세고, 종합에 "이탈 N건(봇완결률에서 제외)"으로 밝힌다.
   - **검증식**: `6개 시트 합 + △이탈 + ❌놓침 = alfTriggered=true 건수`, 그리고 `alf발동 + 미발동 = 총 상담수`. 두 식이 모두 맞아야 저장한다.
   - **세부태그→대분류 매핑**: `분석` 시트에서 학습(각 태그의 ① 제외 이관 최빈 대분류)한다. 명백한 기술장애(`수강/동영상`·"소리/영상 안 나옴") = ③기술오류, 감정·전화고집 발화 = ③감정전화로 보정. 봇 발화 없으면 이 세분은 근사임을 밝힌다.
   - 각 시트: **A열 유형(세부태그)** · **B열~ 일자별 건수**(최신 날짜 건수 내림차순 정렬) · 맨 아래 **합계행**. **새 유형은 해당 시트 맨 아래 새 행**으로 추가.
   - **`요약` 시트도 같이 갱신**: 6대분류 × 일자별 전체 건수 표. `버킷 | 액션 | 기준선(05~06) | [일자 열들...]` 구조로, 각 집계시트 합계행 값을 일자 열에 이어 붙이고 맨 아래 합계행을 갱신한다(집계시트 합과 일치).

5. **분석 결과 표로 정리.** 사용자에게 보여준다.
   ```
   | # | 유형 | 처리(완결/이관/이탈) | 판정 | 근거(태그·발화) | 개선 액션 |
   ```
   - 판정 = ✅적정 / ⚠️없앨수있음 / ❌놓침 / △이탈(미완결).
   - 끝에 **종합**: ⓐ **분모 산출 과정**(전체 N → AI관여 N → 이탈 제외 → 분모 N), ⓑ 이번 배치 등급 분포(✅·⚠️·❌·△·🚫제외 건수), ⓒ `AI상담/*` 태그 건수(특히 고객이탈·오안내·이관안함), ⓓ 가장 반복된 문제 1~2개, ⓔ 직전 점검 대비(봇완결률·없앨수있는이관%·놓침 건수 변화).

5-1. **🔴 미해결 전건 결과표.** step 2-1에서 뽑은 확인 목록을 **한 줄도 빠뜨리지 않고** 아래 표로 낸다. 이게 이 스킬이 실제로 굴러가는지를 결정한다.
   ```
   | 회차 | 개선점 | 직전 상태 | 이번 결과 | 새 상태 |
   ```
   - **사례가 0건이어도 반드시 한 줄 쓴다** — `사례 0건 — N회째 이월`. 빈칸이나 생략은 금지다. 빈칸으로 두면 다음 회차에 목록에서 사라진다.
   - **판정 문구는 셋 중 하나로 시작**: `✅ 확인` / `🟡 부분` / `❌ 그대로·악화` / `🔲 검증 불가(사례 0건)`.
   - **3회 연속 `🔲 검증 불가`면 그대로 넘기지 말고 은주에게 묻는다** — "사례가 안 나와 3회째 판정을 못 했어요. ⓐ 봇에 직접 테스트 문의를 넣어 우회 검증할까요 ⓑ 그냥 닫을까요 ⓒ 계속 대기할까요?"
   - **`미확인`(추적 끊김) 행은 회차당 최소 1건은 결론 낸다.** 상담 분석 없이 확인만 하면 되는 것부터. 그대로 두면 영원히 안 보인다.
   - 이번에 새로 `완료/해소`를 주려면 **2회 연속 재발 없음**인지 먼저 확인한다. 1회차째면 `계속 추적`으로 두고 결과 칸에 "1회차 재발 없음 — 다음 회차에 한 번 더 보고 닫는다"라고 적는다.

5-2. **📐 docs 역방향 점검 (상시).** 봇이 docs보다 잘하고 있는 항목이 없는지 본다. 봇 발화 중 **docs에 없거나 docs와 반대인데 실제로는 맞는 안내**가 있으면 그건 docs가 낡은 것이다. 아울러 은주에게 **"지난 회차 이후 제품에 붙은 기능이나 바뀐 정책이 있나요?"**를 묻는다 — 이 질문이 가장 확실하고, 10차의 배송조회·기출문제 2건 다 이렇게 발견됐다.
   - **과거 회차 비교는 재계산된 계열을 쓴다.** 5~9차는 2026-08-06에 `alfTriggered` 기준으로 전수 재계산했다(27.5 / 39.6 / 39.5 / 39.5 / 46.3%). 그 이전에 기록된 20/34/34/37/36% 계열은 폐기됐다.

8. **노션 갱신 — DB가 먼저, 페이지가 나중.**

   **8-A. 📊 추적 DB 갱신 (필수·먼저).** 상태의 단일 출처다. 여기가 안 맞으면 다음 회차에 또 항목이 새어나간다.
   - **step 5-1 확인 목록의 모든 행**에 대해 `상태`와 `다음 분석 결과`를 갱신한다 (`notion-update-page` + `update_properties`).
     - `다음 분석 결과`는 **기존 텍스트를 지우지 말고 아래에 이어 붙인다** — `기존내용\n[{N}차 {MM-DD}] {판정} — {근거·수치}`. 회차별 경과가 한 칸에 쌓여야 "몇 회째 이월인지"가 보인다.
     - 기존 텍스트가 필요하므로, 수정 전 그 행의 `다음 분석 결과`를 먼저 조회한다.
   - **이번 회차 신규 개선점은 행을 추가**한다 (`notion-create-pages`, parent는 `data_source_id`). `회차`·`점검일`·`분류`·`상태`·`배경 (왜)`·`확인 방법`·`관련 지표/영향`을 채운다.
     - `확인 방법`은 **"다음에 무엇을 몇 건에서 몇 건으로 세면 됐는지 알 수 있나"**로 숫자 기준선을 박아 쓴다. 이게 흐릿하면 다음 회차에 판정이 안 선다.
     - 조치를 막 한 것은 `계속 추적`, 제안만 하고 안 고친 것은 `미확인`.
   - **`회차` select에 이번 회차 옵션이 없으면 먼저 추가**한다(`notion-update-data-source`). 없다고 빈칸으로 두지 말 것.
   - **행을 지우지 않는다.** 해소된 것도 `완료/해소`로 남긴다 — 뒤집힌 전례(8차 docs, 6차 배송현황 docs)가 있어 이력이 근거가 된다.

   **8-B. 추적 페이지 갱신.** 위 노션 페이지(`notion-fetch`로 현재 상태 확인)에 이번 회차 **서술**을 넣는다.
   - **이번 회차 분석 결과 표 추가**: step 4에서 만든 분석 결과를 해당 회차 섹션(`## 📋 분석 결과`)에 넣는다. 봇 발화가 있으면 per-case 표(`# / 유형 / ALF 응대 / 판정 / 문제·위반 규칙 / 개선 액션`), 없거나 수십 건이면 **유형 분포 + 반복 패턴** 요약 표.
   - 이번 회차의 **최대 발견 1~2개**를 서술로 남긴다(수치·chatId 포함).
   - 맨 아래 **"다음 회차 점검 (예정)"** 블록을 갱신한다. 단 여기엔 **이번에 새로 생긴 것 위주로 5~7개만** 쓰고, **미해결 전건은 DB가 관리한다**(여기 다 옮기면 이중 관리가 된다). 마지막 줄에 항상 `DB에서 상태 != 완료/해소 를 먼저 조회할 것`을 남긴다.
   - ⚠️ **상태 표를 페이지에 다시 만들지 말 것.** 2026-08-11에 「누적 해소 현황」 표를 DB로 합치고 페이지에서 지웠다. 표를 또 만들면 DB와 어긋난다.
   - 페이지 표 수정 시 `update_content`의 `old_str`은 **들여쓰기까지 정확히** 맞아야 한다. 표 셀은 탭 들여쓰기가 아니라 **줄 앞 공백 없이** 저장돼 있다. HTML 주석(`<!-- -->`)은 마커로 쓰지 말 것(매칭 안 됨).
   - 개인정보는 노션에도 옮기지 않는다(익명화).

9. **처리완료 이동.** 분석 끝난 상담 파일을 `cs-triage/상담내역/처리완료/`로 옮긴다(원본 보존, 다음 분석 때 중복 방지). `git mv`가 안 되면(미추적 파일) 일반 `mv`를 쓴다.

10. **CX 실행 과제 보드 연결.** 이번 회차 개선점 중 **이 세션 안에서 못 끝내고 따로 시간을 잡아야 하는 것**이 있는지 본다.
    - **올리지 않는 것**: 규칙 파일 수정, docs 보강, 문구 교체 — 여기서 바로 고치는 것들. **추적표가 이미 관리하므로 보드에 넣으면 이중 관리가 된다.**
    - **올릴 것**: 백엔드 조회·실행 연동 확대처럼 몇 시간~며칠을 따로 잡아야 하는 작업.
    - 있으면 **반드시 물어본다** — *"이건 따로 시간이 필요해 보이는데, CX 보드에 올릴까요?"* 자동으로 넣지 않는다. 판단이 들어가는 자리라 자동화하면 안 할 일만 쌓인다.
    - 넣을 때: DB `collection://5a294352-cc03-4c24-a828-be09a28dbc91` (Notion MCP `create-pages`, parent는 `data_source_id`)
      `연결`=KR2 AI상담 / `분기`=26-3Q / `유형`=실행 / `우선순위`는 물어보고 / **`착수일`은 비워둔다**(주간 계획 때 찍는다) / `메모`에 근거(회차·수치)를 남긴다.
    - **반대 방향도 본다**: 보드에 이미 있는 ALF 과제(예: 「ALF 백엔드 조회·실행 연동 확대」)가 이번 회차에 진전됐으면 `상태`·`메모` 갱신을 제안한다.
    - 보드 운영 규칙 전체는 `/cx` 스킬(`.claude/skills/cx/SKILL.md`) 참고.

11. **마무리.** 변경 요약(분석 N건 / 규칙 수정 M건 / **미해결 전건 N건 판정** / 로그·노션 DB·엑셀 갱신 / 파일 이동 / 보드 반영)을 보고하고, 끝에 "GitHub에 push할까요? (`cspush`)"를 묻는다.
    - **보고 전 자가 점검 3가지**: ⓐ step 2-1 확인 목록의 행 수 = step 5-1 결과표의 행 수인가(하나라도 빠지면 다시) ⓑ DB에서 `완료/해소`로 바꾼 행이 전부 2회 연속 재발 없음인가 ⓒ `미확인` 행 중 이번에 결론 낸 것이 최소 1건인가. **셋 중 안 되는 게 있으면 그 사실을 그대로 보고한다** — 조용히 넘기면 그게 추적이 끊기는 순간이다.

## 로그 출력 형식 (ALF_개선로그.md에 누적)

파일 맨 위 **현황 요약**은 매번 덮어쓰고, 그 아래 **개선 이력**에 새 회차를 최신순으로 끼워넣는다.

```markdown
### {오늘 날짜} | {N}차 점검
- **분석 대상**: {파일명/건수, 어떤 유형 위주}
- **분모 산출**: 전체 N → alf발동 N → 이탈 제외 → 분모 N
- **결과**: ① 봇완결 N(x%) / ⚠️ 없앨수있는이관 N / ✅ 정당이관 N / ❌ 놓침 N / △ 이탈 N
- **잘 된 점**: ...
- **문제점**: (위반 규칙·오답·불필요 이관)
- **미해결 전건 점검**: (step 5-1 표 — 확인 목록 전건. 사례 0건도 "N회째 이월"로 한 줄씩)
- **개선 액션**: → {수정한 규칙 파일}에 {무엇을} / 또는 "제안만, 미반영"
- **직전 대비**: (지난번 지적이 이번에 좋아졌나)
- **다음 점검 때 확인할 것**: (신규 위주 5~7개. 미해결 전건은 노션 DB가 관리)
```

**현황 요약 블록의 "주요 미해결 이슈"는 DB의 `미해소`·`부분 확인` 행과 어긋나면 안 된다.** 로그를 갱신할 때 DB 상태를 그대로 반영한다 — 둘이 다르면 어느 쪽이 맞는지 아무도 모르게 된다.

## 주의
- 비개발자다. 유형 코드·규칙 위반을 짚을 땐 "왜 그게 문제인지" 한 줄로 쉽게 설명한다.
- 상담 내역에 고객 개인정보(이름·전번·주소)가 있으면 로그에 그대로 옮기지 말고 마스킹하거나 "○○ 고객"으로 익명화한다.
- 규칙 파일 수정·로그 저장은 사용자 확인 후. 파일 삭제는 하지 않는다(이동만).
- 상담 건수가 많으면(수십 건+) 유형별로 묶어 표본·패턴 위주로 정리하고, 무엇을 표본으로 골랐는지 밝힌다.
