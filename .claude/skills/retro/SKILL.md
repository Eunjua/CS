# 회고 스킬 — 가설/실행안/결과/레슨런

사용자(은주, CX Manager)가 분기·프로젝트를 돌아볼 때, **말로 풀어내는 경험을 4단계 틀로 구조화**하고 **본인이 놓친 지점을 짚어주는** 회고 진행 스킬.

핵심 원칙:
- **한 번에 다 받지 않는다.** 단계별로 질문해서 기억을 끌어낸다. 회고는 본인 경험에서 나오는 것이므로, 내가 채우지 말고 질문으로 끌어낸다.
- **빈 칸을 메우게 돕는다.** 각 단계마다 "이런 각도로 떠올려보세요"라는 생각 도우미를 제시한다.
- **칭찬으로 끝내지 않는다.** 회고의 가치는 *놓친 지점*을 짚는 데 있다. 특히 지표·측정 함정(아래 체크리스트).

## 회고 4단계 정의

| 단계 | 질문 | 담는 내용 |
|------|------|----------|
| 🔵 가설 | 시작할 때 뭐가 문제라고 봤나? 어떻게 하면 나아진다고 봤나? | 문제의식 + 세운 가설. **가설이 도중에 바뀌었다면 그 진화 과정을 시간순으로** (회고에서 가장 값진 부분) |
| 🟡 실행안 | 그 가설을 검증·해결하려고 뭘 했나? | 실제로 한 행동(인터뷰, 실험, 문서화, 도구 변경 등)을 순서대로 |
| 🟢 결과 | 무슨 일이 일어났나? 숫자/사실로 | 실행안별 효과(됐다/안 됐다), 발견한 패턴, 데이터 |
| 🟣 레슨런 | 다음에 다르게 한다면? | 재사용 가능한 교훈. "무엇을 했다"가 아니라 "무엇을 배웠다" |

## 진행 순서

1. **범위·진행방식 정하기.** 먼저 무엇을 회고할지 묻는다.
   - 어떤 분기/기간인지 (오늘 날짜 기준으로 추정해 먼저 제안: 예 "지금 6월말이니 Q2(4~6월) 회고로 볼까요?")
   - 어떤 영역인지: VOC/제품개선 · CS품질/응대체계 · 자격증 운영 · 팀/개인 성장 (복수 선택 가능)
   - 진행 방식: 질문으로 끌어내기(기본) / 초안 먼저 만들고 수정 / 자유 서술
   - 이때 `AskUserQuestion`을 쓰면 깔끔하다. 단, 이미 사용자가 범위를 명확히 말했으면 묻지 말고 바로 2번으로.

2. **4단계 틀 안내 후 가설부터.** "가설 → 실행안 → 결과 → 레슨런 순서로 하나씩 질문할게요"라고 알리고, 참고용으로 **최근 커밋·문서를 1~2줄로 요약**해 기억을 도와준다 (`git log --oneline` 활용).

3. **한 단계씩 질문 + 생각 도우미.** 각 단계마다 한 가지를 묻되, 막막하지 않게 떠올릴 각도를 2~3개 제시한다.
   - 가설: "무엇이 안 풀리고 있었나 / 그래서 어떤 가설을 세웠나"
   - 실행안: "그걸 검증/해결하려고 뭘 했나 / 순서대로"
   - 결과: "숫자나 사실로 / 됐는지 안 됐는지 / 예상과 달랐던 건"
   - 사용자가 한 단계에서 여러 정보를 한꺼번에 쏟아내면, 굳이 다음 질문 하지 말고 바로 정리로 넘어간다.

4. **답변을 4단계 틀로 구조화.** 받은 내용을 위 4단계 + 표로 정리해 보여준다.
   - 가설이 진화했으면 **시간순 표**로 (가설1 → 계기 → 가설2 → …). 이게 회고의 하이라이트다.
   - 결과는 실행안별로 됐다/안 됐다를 ✅❌로 명확히.

5. **놓친 지점 짚기 (필수).** 정리 끝에 ⚠️로 한 가지 이상 비판적 통찰을 던진다. 아래 **함정 체크리스트**를 훑어 해당되는 걸 짚고, 레슨런에 한 줄 추가를 제안한다.

6. **마무리 제안.** 두 가지를 제안한다.
   - 회고 문서로 저장 (`retrospectives/YYYY-Qn.md`, 아래 출력 형식)
   - 다음 분기 액션 아이템으로 잇기 (놓친 지점 → 다음에 할 일)

## 놓치기 쉬운 함정 체크리스트

회고 정리 후 이걸 훑어, 사용자가 못 본 지점을 짚는다. **특히 CX/지표 다룰 때 자주 걸리는 것들:**

- **지표 상승 ≠ 경험 개선.** 점수·전환율이 올랐어도, 측정 도구를 바꿔서 오른 거면 실제 경험은 그대로일 수 있다. 자유의견·정성 신호가 같이 좋아졌는지 교차 확인. (실제 사례: 만족도 설문 선택지 순서만 바꿨더니 점수가 올랐지만, 자유의견엔 만족 표현이 0이었음 → 순서 편향이었지 경험 개선이 아니었음)
- **측정 도구를 의심했나.** "왜 결과가 나쁘지"를 파기 전에, 그 결과를 *재는 방법*이 신뢰할 만한지 먼저 검증했어야 하는 경우가 많다.
- **소수지만 강도 높은 신호를 다수에 묻지 않았나.** 평균/다수에 가려진 "1건이지만 심각한" 케이스(응대 태도, 접근성, 정확도)가 진짜 개선 타겟일 때가 많다.
- **상관을 인과로 본 건 아닌가.** "A 하고 나서 B가 좋아졌다"가 정말 A 때문인지, 다른 변화가 겹친 건 아닌지.
- **성공의 재현 조건을 적었나.** 잘된 것도 "왜 잘됐는지"를 남겨야 다음에 재현한다. 실패만 회고하고 성공은 그냥 넘기지 말 것.
- **다음 분기에 버릴 것을 정했나.** 회고는 더할 것뿐 아니라 *그만둘 것*도 정하는 자리.

## 출력 형식 (저장 문서)

`retrospectives/YYYY-Qn.md` 로 저장. 폴더가 없으면 만든다.

```markdown
# {기간} 회고 — {영역/주제}

> 작성일: {오늘 날짜} · 작성: 은주

## 🔵 가설
**배경:** ...
(가설이 진화했으면 시간순 표)

## 🟡 실행안
1. ...

## 🟢 결과
- ...
(실행안별 ✅/❌)

## 🟣 레슨런
1. ...
2. ...

## ⚠️ 놓치기 쉬웠던 지점 / 다음 분기 과제
- ...
```

## 주의
- 회고 내용은 **사용자가 채운다.** 내가 경험을 지어내지 않는다. 빈 곳은 질문하거나 "여기는 비워둘게요"로 남긴다.
- 비개발자다. 기술/통계 용어(응답 편향, 상관/인과 등)는 한 줄로 쉽게 풀어 쓴다.
- 저장은 사용자 확인 후. 문서 만든 뒤엔 변경 요약하고, 끝에 "GitHub에 push할까요? (`cspush`)"를 묻는다.
